> 配套:[01-8周学习计划表.md](01-8周学习计划表.md)(什么时候做) · [02-资源获取清单.md](02-资源获取清单.md)(用什么跑) · 术语见 [CONTEXT.md](CONTEXT.md)
> 本文定位:01 给「时间线」,本文给「做成什么样」—— 三作品的**选题 / 技术栈 / 验收标准**一次定稿。
> 一句话叙事:**三作品层层复用,讲成一个故事**——作品一搭全栈工程规范知识库(RAG,含后端 Python + 前端 TS 两侧规范);作品二把"会查知识库的 Agent"工程化(编排+权限);作品三用同一套规范 RAG + 编排,做前后端代码 Review。简历上是「一条线」、且天然覆盖全栈,不是「三个孤立 demo」。

---

## 零、设计总原则(三作品共用)

1. **差异化靠领域,不靠技术新**:用你的全栈(后端 + 前端)底子选题,别做烂大街的"通用文档问答 / 天气查询 Agent"。
2. **护城河是工程化**:后端下水道能力(接口抽象、状态机、容错降级、权限控制、并发调度)才是碾压应届/转码者的点,框架 API 不是。
3. **每个作品交三件套**:能跑的 live demo + 量化指标 + 能讲透"为什么这么设计 / 踩了什么坑"。
4. **主语言 Python**:Java/TS 只作杠杆建立直觉,产出与简历主语言都是 Python。
5. **推理策略继承 02**:Embedding 本地 `bge-m3` · LLM 生成 GLM 免费 API 优先(本地 `qwen2.5:7b` 兜底)· Rerank 走免费 API。本地↔API 只差一个 `base_url`。

## 一、共享技术底座(一次定,三处用)

| 层 | 选型 | 跑哪 | 理由 |
|---|---|---|---|
| 语言 / 包管理 | Python 3.12 + `uv` | 本地 | 主语言短板要补,硬通货 |
| LLM 生成 | GLM-4.7-Flash(API) | 免费 API 优先 | 把 16GB 留给 Docker/IDE;要工程体感再本地 `qwen2.5:7b` |
| Embedding | `bge-m3` | 本地 | 小、快、带得动,省额度 |
| 向量库 | pgvector | 本地 Docker | 复用你的 SQL/PG 经验;**用 `langchain-postgres` + `psycopg3`,连接串 `postgresql+psycopg://`**(旧 `langchain_community.PGVector` 已弃用) |
| RAG 框架 | LangChain | — | 主流,生态全 |
| Rerank | `bge-reranker`(硅基流动 API) | 免费 API | 16GB 再叠 cross-encoder 太紧 |
| Agent 编排 | LangGraph | — | 生产级主流,你的状态机经验直接复用 |
| 工具层 | 自写 Tool Registry | 本地 | W5 手写 ReAct 的产物,三作品共用 |
| Web UI | Streamlit | 本地 | 最快出 demo |
| 展示 | GitHub Pages | — | 仓库 `ai-agent-portfolio`,免费 |

**复用关系(作品三是前两个的集大成):**

```
作品一(RAG 规范库) ──┐
                      ├──> 作品三(研发提效 Agent)
作品二(LangGraph 编排 + Tool Registry)─┘
```

**语言约定(前后端混合的落法)**:编排 / RAG / Agent 代码统一 **Python**(AI 应用岗 JD 提及 Python 125 次 vs TS 15 次,简历主语言必须 Python);**知识域和被处理的代码**才分前后端 —— 作品一规范库收 **后端 Python/API + 前端 React/TS** 两侧规范,作品三 Review Agent 同时审 **Python 后端 + TS 前端** 代码。后端不引入 Java/Go(那是另背一个知识域);Java 仅作可选杠杆(Spring AI/LangChain4j 建直觉),不进产出。

## 二、作品一:企业知识库问答(RAG)

- **周次**:W3 启动选题 → W4 出 v1.0
- **选题定稿(推荐)**:**全栈工程规范知识库问答**(后端 Python/API 规范 + 前端 React/TS 规范,合一个库)
  - 备选:聚焦单侧(纯后端,如 FastAPI/Django 文档;或纯前端,如 React 文档助手)
  - 理由:你全栈,能亲自验收答案对错(别的领域判断不了质量);一个库同时喂作品三的前后端 Review,复用闭环;"全栈规范"本身就是差异化卖点。
- **技术栈**:`langchain-postgres`(pgvector) + 本地 `bge-m3` embedding + GLM 生成 + `bge-reranker`(API) + Streamlit
- **核心链路**:文档加载 → chunking → embedding → pgvector → 检索 → rerank → 拼 prompt → 带引用生成
- **工程化亮点(护城河,务必做)**:检索为空的兜底回答 · LLM 超时重试 · 并发查询调度
- **验收标准**:

| 维度 | 目标 |
|---|---|
| 引用溯源 | 每条回答标注来源文档片段,覆盖率 100%(面试必问) |
| rerank 增益 | 给出量化:Top-3 命中率 rerank 前→后(目标如 65%→88%) |
| 评估 | 自建 ≥15 条测试问答对,出召回率/准确性对比表 |
| chunking 实验 | size 500 vs 1000、有无 overlap 的检索质量对比记录 |
| demo | Streamlit Web UI 可现场演示 |
| 讲透 | 能白板画全链路 + 讲清"为什么 pgvector 而非 Milvus" |

- **产出物**:作品一 v1.0 + RAG 评估报告 + 博客①《从 0 搭一个带引用溯源的企业知识库 RAG》
- **简历话术**:"基于 pgvector 自建全栈工程规范 RAG,引入 rerank 将 Top-3 命中率从 X% 提升到 Y%,带引用溯源 + 检索兜底降级。"

## 三、作品二:有自主规划的业务 Agent(LangGraph)

- **周次**:W6 出 v1.0(本周偏重)
- **选题定稿(推荐)**:**数据库运维 Agent(带误删防护)**
  - 备选:智能运维助手(查日志/调接口/诊断)、API 测试 Agent
  - 理由:报告点名高频面试题"Agent 操作数据库怎么防误删",这个选题天然把你的护城河(权限控制 + HITL)摆到 C 位,后端老兵的运维直觉能讲透。
- **技术栈**:LangGraph(State/Node/Edge + 持久化 + human-in-the-loop) + 作品一的 RAG(让 Agent 能查知识库) + 自写 Tool Registry + GLM(多步工具调用要可靠 FC) + Streamlit
- **核心流程**:规划 → 工具调用 → 反思 → 输出
- **工程化亮点(重点,你的主场)**:

| 亮点 | 说明 |
|---|---|
| 权限控制 + HITL | 危险操作(删/改库)前**强制人工确认**——做成最佳示范 |
| 终止三件套 | 最大步数 + 重复动作检测 + 参数去重,防死循环/幻觉式调用 |
| 容错降级 | 工具调用失败重试、超时降级、状态持久化 |
| 并发调度 | 多工具/多查询并发 |

- **验收标准**:

| 维度 | 目标 |
|---|---|
| 自主多步 | 能独立完成 规划→执行→反思 的多步任务 |
| HITL 拦截 | 危险操作触发人工确认,拦截率 100% |
| 工具成功率 | 量化工具调用成功率(目标 ≥90%)、平均响应时长 |
| 防失控 | 能用代码佐证死循环防护与容错降级 |
| 讲透 | 能讲清"为什么 LangGraph 而非裸写循环" |

- **产出物**:作品二 v1.0 + 博客②《用 LangGraph 做一个带误删防护的业务 Agent:后端工程师视角》
- **简历话术**:"用 LangGraph 编排带自主规划的运维 Agent,危险操作经 HITL 拦截 + 最小权限,工具调用成功率 X%,含失败重试与状态持久化。"

## 四、作品三:研发提效 Agent(AI Coding 方向 · 差异化王牌)

- **周次**:W7 出 v1.0(与面试突击双线,作品线约 12h)
- **选题定稿(推荐)**:**全栈代码 Review Agent**(读 diff → 按规范给 review 意见,支持 Python 后端 + TS 前端两种语言)
  - 备选 1:JS→TS 迁移助手(吃前端,差异化强;但正确性风险高,务必**做小**:限定单文件 + 单一迁移规则集)。
  - 备选 2:测试用例生成 Agent(读函数 → 生成单测,可量化:生成测试通过率 + 覆盖率)。
  - 理由:直接对接 AI Coding 岗;**复用作品一的全栈规范 RAG**(Review 时查规范)+ 作品二编排,不必再造轮子;"前后端都能审"是全栈差异化卖点,三作品叙事闭环。
- **技术栈**:复用作品一 RAG(查规范) + 作品二 LangGraph 编排 + Tool Registry;新增 diff 解析 / 文件读取工具
- **验收标准**:

| 维度 | 目标 |
|---|---|
| 能跑 | 给一段真实 diff,产出结构化 review 意见(命中规范条目 + 定位行号) |
| 复用证据 | 明确复用作品一 RAG 查规范、作品二编排,README 说清 |
| 量化 | 选题相关指标:Review 规则覆盖数(前后端) / 测试生成通过率 + 覆盖率 / 迁移限定集正确率 |
| 文档 | README + 架构图 + 量化指标齐全 |

- **产出物**:作品三 v1.0 + **三作品统一展示页**(GitHub Pages,含 demo 入口)

## 六、简历量化指标汇总(投递口径,收口)

> 简历只认"判断 + 量化",不堆 API。下表是三作品要凑出的硬指标,开发时就按这个口径记数据。

| 作品 | 量化指标(示例口径,以实测为准) |
|---|---|
| 作品一 RAG | Top-3 命中率 rerank 前→后(如 65%→88%);引用溯源覆盖 100%;评估集 ≥15 条 |
| 作品二 Agent | 工具调用成功率 ≥90%;HITL 危险操作拦截 100%;平均响应时长 |
| 作品三 Coding | Review 规则覆盖数(前后端) / 测试通过率 + 覆盖率 / 迁移限定集正确率(三选一) |

## 七、风险与"做小"预案

| 风险 | 预案 |
|---|---|
| 三作品做不完 | **保作品一(RAG)+ 作品二(Agent)**,作品三缩成 demo 级小工具;质量 > 数量 |
| 选了迁移助手但正确性翻车 | 限定单文件 + 单一规则集做小;或退回代码 Review / 测试生成 |
| 16GB 跑 7B 卡 | 生成走 GLM API;embedding 仍本地 bge-m3;rerank 走 API |
| 选题不熟无法验收答案 | 收窄到你最熟的单侧(后端 Python 或前端 React),领域熟才能判断 demo 质量 |
