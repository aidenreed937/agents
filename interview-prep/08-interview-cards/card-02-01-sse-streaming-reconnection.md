# 面试卡：Web/客户端到 LLM 的 SSE 流式中断如何恢复？

**模块**：02-web-fullstack ｜ **难度**：高级 ｜ **熟练度**：A

---

### 1. 30 秒电梯回答
SSE 流式容灾的核心是**“任务执行状态与客户端流式传输解耦”**。
- **解耦与事件缓存**：服务端将推理任务后台化（持久化 `task_id`），生成的事件序列带有单调递增 `id` 写入短 TTL 缓存队列（如 Redis）；网络抖动不掐断后台任务；
- **断点续传协议**：客户端断线重连时携带 `Last-Event-ID`，服务端从缓存切片补发缺失事件并平滑续接实时流；超过 TTL 窗口则降级为按 `task_id` 轮询最终归档状态。

---

### 2. 深入原理
1. **执行与传输解耦**：
   - 用户发起请求时，服务端创建 `task_id` 并持久化（状态为 `RUNNING`），后台协程/线程负责驱动 Agent 运行。
   - SSE 连接仅是后台任务的**视图投射管道**。网络抖动或客户端切后台断开 HTTP 连接，不掐断后台任务（除非收到取消信令或超时熔断）。
2. **事件序列化与缓存缓冲**：
   - 服务端下发的每条 SSE 消息携带单调递增的 `id`，例如：
     ```http
     id: msg_001_seq_42
     event: delta
     data: {"content": "正在检索"}
     ```
   - 服务端将事件序列暂存在 Redis List 中，保留 TTL（如 10 分钟）。
3. **断点重连协议（Reconnection Handshake）**：
   - 客户端监听 `EventSource` 的 `onerror` 事件，采用指数退避重连，请求头携带 `Last-Event-ID: msg_001_seq_42`。
   - 服务端接收后从 Redis 切片补发 `seq > 42` 的事件，补齐后无缝切回实时流；客户端依据 `seq` 去重，防止重推乱序。

---

### 3. 工程取舍与边界
- **长连接保活与中间代理防断**：企业网关（Nginx、ALB）通常有 60s~120s 空闲超时断开机制。服务端每 15 秒发送轻量心跳注释（`: keep-alive\n\n`），且 Nginx 必须配置 `proxy_buffering off;` 防止代理层缓冲积压。
- **内存消耗 vs 恢复窗口权衡**：事件不无限期保留，只在 Redis 中设定短 TTL（如 10 分钟）。超出窗口的极端重连，客户端降级为根据 `task_id` 查询任务最终归档状态并整页拉取。

### 4. 高频追问应对
- **追问 1：如果客户端断线后永远不回来了，服务端后台任务还在一直烧 Token 怎么办？**
  - **应对**：引入任务心跳租约机制或全局硬超时（如单任务上限 3 分钟）。对于多步骤复杂 Agent，每完成一个主要 Step 检查一次客户端在线状态与取消信号。
- **追问 2：为什么选用 SSE 而不是 WebSocket？**
  - **应对**：权衡在于复杂度与单双向需求。LLM 生成场景绝大多数是“单次 Prompt 触发，服务端持续流式下发”的单向流。SSE 基于标准 HTTP，天然穿透企业防火墙、支持 HTTP/2 多路复用且浏览器原生支持自动重连；WebSocket 应用层自建心跳、重连与鉴权握手成本更高。
- **追问 3：在 Spring Boot 或 FastAPI 中如何防止长连接耗尽工作线程？**
  - **应对**：必须使用**异步非阻塞 I/O**。FastAPI 中使用 `async generator` + `StreamingResponse`；Spring Boot 中必须使用 `ResponseBodyEmitter` 或 WebFlux `Flux<ServerSentEvent>`，严禁在阻塞式 Tomcat 工作线程中用 `Thread.sleep` 模拟推送。
