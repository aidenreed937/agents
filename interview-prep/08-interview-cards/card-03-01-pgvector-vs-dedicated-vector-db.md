# 面试卡：RAG 向量存储选型：pgvector 与专有向量库的权衡

**模块**：03-database-system ｜ **难度**：高级 ｜ **熟练度**：A

---

### 1. 30 秒电梯回答
向量存储选型的核心是**数据规模、事务一致性与系统复杂度的权衡**。
- **千万级以内优先 pgvector**：在单库内原子实现结构化业务数据与向量切块的统一 ACID 事务、强多租户行级安全隔离（RLS），且无需维护跨系统同步与额外中间件；
- **超亿级规模按需引入专有库**：仅在向量规模达数千万至亿级、需要微秒级超高并发近邻检索与分布式 Sharding 水平扩展时，才考虑引入 Milvus 或 Qdrant 等独立向量库。

---

### 2. 深入原理
1. **PostgreSQL + pgvector 的优势与机制**：
   - **单库 ACID 与事务原子性**：业务数据（租户、权限、文档元数据）与向量切块（Chunks）在同一数据库事务中原子写入，从根源规避“业务库已删除但向量库仍残留脏数据”的双库一致性问题。
   - **混合过滤（Hybrid Filtering）**：直接在 SQL 的 `WHERE` 子句中做多维度属性过滤（如 `workspace_id = 'ws_1' AND role_level >= 2`），协同向量余弦距离计算。
   - **索引机制选型**：
     - `IVFFlat`（倒排列表）：构建快、内存占用小，但召回率略低，适合大批量离线导入后再建索引；
     - `HNSW`（分层可导航小世界图）：构建较慢、内存开销高，但检索速度快且召回率高，天然支持持续增量写入。
2. **专有向量数据库的适用场景**：
   - 针对超高维向量计算做了底层 SIMD/GPU 硬件指令加速与专有内存分区架构，支持分布式 Sharding 水平扩展，适合超亿级向量的高吞吐搜索。

---

### 3. 工程取舍与边界
- **两阶段写入与权限滞后风险**：若采用“业务库 + 专有向量库”，文档增删改需跨系统双写；若网络抖动会导致数据不一致，且文档权限变更无法即时同步到向量库 Payload，易引发同步窗口期的越权泄漏风险。
- **内存驻留边界与性能拐点**：`pgvector` 使用 HNSW 时，必须确保索引图完全载入 `shared_buffers` 或系统 RAM。当单表向量达到千万级且超出可用内存时，频繁磁盘 I/O 会导致查询 QPS 从数千骤降至个位数，此时需考虑分区表、标量量化或迁移专有库。

---

### 4. 高频追问应对
- **追问 1：在多租户企业知识库场景中，pgvector 如何防止租户间数据越权？**
  - **应对**：利用 PostgreSQL 的 **Row-Level Security (RLS)** 或在查询视图中强制注入 `tenant_id`。所有相似度计算仅在当前租户的数据子集内发生，从物理执行层切断提示词注入引发的跨租户检索漏洞。
- **追问 2：数据量涨到多大时，pgvector 会出现明显的性能拐点？**
  - **应对**：通常在单表 1000 万到 2000 万行向量左右（视 1536 维等向量维度及服务器内存大小而定）。一旦 HNSW 索引超出物理内存上限，必须通过按租户/年份分表、HNSW 参数调优（缩小 `m` 与 `ef_construction`）或引入专有向量库破局。
- **追问 3：为什么很多团队一上来用 Milvus 等专有库反而踩坑？**
  - **应对**：主要是忽略了**跨系统事务一致性与权限变更滞后性**。引入额外分布式组件不仅增加了运维和故障点，还需要配套开发本地消息表或补偿机制来维持双库对齐。
