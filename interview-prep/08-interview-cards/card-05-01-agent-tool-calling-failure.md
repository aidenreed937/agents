# 面试卡：Agent 工具调用失败怎么处理？

**模块**：05-agent-engineering ｜ **难度**：高级 ｜ **熟练度**：B

---

### 1. 30 秒电梯回答
Agent 工具调用的治理核心是**“错误分级自治与带副作用操作的幂等防线”**。
- **错误分类与自纠错**：将异常划分为参数幻觉、网络抖动、业务拒绝与致命异常。参数校验失败（Schema Mismatch）将错误详情反哺 Prompt 触发模型自纠错，只读网络异常执行指数退避；
- **副作用防重与降级**：对写操作工具（转账/发邮件/写库）强制注入全局 `idempotency_key` 抵御重试副作用；不可恢复错误及时阻断并注入结构化错误上下文，由模型决策优雅降级。

---

### 2. 深入原理
工具调用的生命周期包含四阶段，错误处理策略因阶段而异：
1. **参数解析阶段（Schema Validation）**：模型生成的 JSON 不符合 Tool 定义（缺少字段、类型错误）。
   - **对策**：使用 Pydantic/Zod 校验失败后，将校验错误明细（如 `{"error": "field 'amount' must be positive float"}`）封装为 `tool_message` 塞回上下文，触发模型自纠错（通常允许 1~2 次）。
2. **鉴权与前置检查（Pre-check）**：租户隔离校验或权限校验未通过。
   - **对策**：直接阻断执行，不进行任何重试，直接返回结构化业务错误码，告知模型权限不足。
3. **工具执行阶段（Execution）**：外部 API 500、超时或网络中断。
   - **对策**：对只读类工具（GET/Search）启用指数退避重试（带 Jitter）；对写操作工具（POST/扣款/发邮件），强制要求注入 `idempotency_key`，避免重试引发重复副作用。
4. **结果消费阶段（Consumption）**：工具返回的内容超出上下文窗口或格式无法解析。
   - **对策**：截断超出限制的大文本，提取结构化摘要后再交由模型处理。

---

### 3. 工程取舍与边界
- **盲目重试 vs 上下文污染**：如果工具返回的错误信息过于复杂，模型容易陷入重复调用相同错误参数的死循环。必须设置工具循环的最大迭代深度（Max Steps，通常建议 5~8 次）以及针对同一工具连续失败的熔断计数器。
- **重试的幂等代价**：对于写操作工具，如果外部第三方接口不支持幂等键，宁可失败挂起等待人工干预，也绝不能让 Agent 自动重试。

---

### 4. 高频追问应对
- **追问 1：如果工具执行成功但网络超时导致 Agent 没收到响应，重试导致重复扣款怎么防？**
  - **应对**：推行“两阶段提交”或“业务幂等键”。Agent 在生成调用请求时，Runtime 必须为该次动作绑定一个确定性的 `action_execution_id` 作为幂等键，下游业务系统必须落库该幂等键，若已存在则直接返回之前的结果，避免二次执行。
- **追问 2：模型反复生成错误的参数，导致 Agent 陷入死循环怎么办？**
  - **应对**：设置双重防护：一是局部计数器（同一工具连续报错 2 次即终止并强制转降级提示）；二是全局步数上限（Max Steps 兜底），达到上限直接抛出系统级错误并记录告警。
- **追问 3：生产环境如何排查某次工具调用到底卡在哪一步？**
  - **应对**：依靠全链路 Tracing（如 Langfuse / OpenTelemetry），为每次 Agent 运行生成统一的 `trace_id`，将模型输入输出、工具解析耗时、外部 API 请求/响应状态码和异常堆栈按 Span 结构化打平记录。
