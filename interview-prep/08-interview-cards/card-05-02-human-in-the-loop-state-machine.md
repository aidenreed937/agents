# 面试卡：Agent 状态持久化与 Human-in-the-loop（人工审批）如何实现？

**模块**：05-agent-engineering ｜ **难度**：高级 ｜ **熟练度**：A

---

### 1. 30 秒电梯回答
Agent 人工介入（HITL）的核心是**将黑盒推理建模为“基于 Checkpoint 快照的可中断、可恢复状态机”**。
- **高危拦截与快照持久化**：当解析出高危工具（写库/扣款/发邮件）时，Runtime 拦截物理执行，将上下文及待决动作（Pending Actions）序列化存入 Checkpoint 并释放工作线程；
- **异步审批与无损唤醒**：工作流置为等待审批状态，待外部工单或用户决策回调后，Runtime 依据 Thread ID 载入历史快照，注入人工决策（同意/篡改参数）并继续推进后续图节点。

---

### 2. 深入原理
1. **状态模型定义（State Schema）**：
   - 核心状态包含：`messages`（多轮对话与工具消息序列）、`workflow_data`（业务中间变量）、`next_action`（待执行的高危工具与入参）、`approval_status`。
2. **两阶段执行与拦截（Intercept Hook）**：
   - 工具严格区分为“安全只读类”与“高危写操作类”。
   - 运行循环在解析出 Tool Call 后先经过安全拦截器。若工具标记为 `require_approval=True`，Runtime 构造包含待执行参数的审批事件，**不触发物理工具函数**。
3. **断点持久化与资源释放**：
   - 将 Agent 内存与图状态序列化落库（PostgreSQL / Redis），生成对应的 `checkpoint_id` 与全局唯一 `thread_id`。
   - 立即释放工作协程/线程资源，避免长耗时阻塞挂起消耗服务吞吐。
4. **唤醒与状态推进（Resume & Transition）**：
   - 审批人点击“同意”或“修改参数后同意”后，回调接口携带 `thread_id` 触发唤醒。
   - Runtime 恢复快照，将审批决策作为 `tool_message` 写回上下文，推动状态机从断点节点继续执行后续步骤。

---

### 3. 工程取舍与边界
- **参数防篡改（Time-of-Check to Time-of-Use）**：审批人看到的参数必须与最终执行的参数完全一致，防范前端传参篡改。恢复执行时严格使用快照中已持久化的工具调用载荷，或仅允许审批人修改明确许可的白名单字段。
- **审批超时与版本冲突**：长周期审批可能面临外部业务状态变更（如库存不足、价格过期）。必须为待审批状态设置合理 TTL，并在唤醒后执行真实工具前执行“二次前置校验”。

---

### 4. 高频追问应对
- **追问 1：如果审批人拒绝，或者修改了参数，状态机如何向模型反馈？**
  - **应对**：若“拒绝”，以 `tool_message` 形式注入上下文：`{"status": "rejected", "reason": "审批人驳回：超出单笔支出额度"}`，模型据此感知并重新规划降级方案；若“修改后同意”，在上下文中记录修正后的参数及真实执行结果。
- **追问 2：LangGraph 中的 Checkpointer 是如何实现暂停与恢复的？**
  - **应对**：LangGraph 在节点间设计了 `interrupt_before` / `interrupt_after` 机制。引擎在执行到该节点时自动写入 Checkpoint 并退出循环；外部通过 `Command(resume=...)` 传入审批输入重新调用，引擎根据 `thread_id` 定位最新快照继续推进。
- **追问 3：为什么不直接在代码里用 `sleep()` 或挂起 Future 来等待用户审批？**
  - **应对**：生产环境下不可接受。进程重启、服务扩缩容或 Pod 漂移会导致内存挂起的线程与上下文彻底丢失，且会霸占工作线程与数据库连接池，必须依赖持久化外部存储实现无状态唤醒。
